An OpMode that runs silently and gives drivers no feedback is difficult to debug and frustrating to operate. The FTC SDK provides three overlapping feedback channels: the **Telemetry API** to display sensor data and status on the Driver Station screen, the **Gamepad** class to read joystick and button inputs from up to two controllers, and — for teams using Xbox or PS4 gamepads — **rumble and LED output** to signal events like game-time milestones or sensor thresholds. This page covers all three in depth.

---

## Telemetry API

Telemetry transmits key-value data from the Robot Controller to the Driver Station app over the USB or Wi-Fi connection. The SDK throttles transmissions to reduce bandwidth use (default: 250 ms between sends), so calling `telemetry.update()` does not guarantee an immediate packet — it schedules the next send.

### Basic data lines

The most common pattern pairs a string caption with a value:

```java
telemetry.addData("Left Encoder",  leftDrive.getCurrentPosition());
telemetry.addData("Right Encoder", rightDrive.getCurrentPosition());
telemetry.addData("Heading (deg)", imu.getRobotYawPitchRollAngles().getYaw(AngleUnit.DEGREES));
telemetry.update(); // Required in LinearOpMode to flush to Driver Station
```

<Note>
  `telemetry.update()` is **required** in `LinearOpMode` — without it, nothing is ever sent to the Driver Station. In iterative `OpMode` (subclasses of `OpMode`), the framework automatically calls `telemetry.update()` at the end of each `loop()` invocation, so explicit calls are optional there. When in doubt, call it explicitly.
</Note>

`addData` accepts any `Object` as the value argument and calls `toString()` on it, so you can pass integers, doubles, booleans, or even enum values directly.

### Printf-style formatting

For more precise numeric formatting, pass a format string and arguments:

```java
telemetry.addData("Drive Power", "%.2f", drive);
telemetry.addData("Battery",     "%.1f V", getBatteryVoltage());
telemetry.addData("Loop Time",   "%5.1f ms", loopTime.milliseconds());
```

This mirrors Java's `String.format()` syntax and is useful when you want consistent decimal places in your display.

### Composing multi-value lines

`telemetry.addLine()` returns a `Telemetry.Line` object that supports chaining multiple `addData()` calls onto a single display row:

```java
telemetry.addLine("Left Joystick | ")
    .addData("x", gamepad1.left_stick_x)
    .addData("y", gamepad1.left_stick_y);

telemetry.addLine("Right Joystick | ")
    .addData("x", gamepad1.right_stick_x)
    .addData("y", gamepad1.right_stick_y);
```

### Lazy evaluation with lambdas

Computing certain values (like battery voltage) is expensive enough that you should skip the computation when telemetry is not actually being transmitted. The `Func<T>` interface lets you register a lambda that is only invoked when the SDK is about to send a packet:

```java
// getBatteryVoltage() is only called when telemetry is actually transmitted
telemetry.addData("voltage", "%.1f volts", new Func<Double>() {
    @Override
    public Double value() {
        return getBatteryVoltage();
    }
});
```

### Telemetry log

The **log** panel is a scrolling message area below the main data lines. It is useful for recording one-time events (task completed, sensor threshold crossed, autonomous branch taken) without overwriting the live data area. Log entries persist on screen until they scroll off the top:

```java
telemetry.log().setDisplayOrder(Telemetry.Log.DisplayOrder.OLDEST_FIRST);
telemetry.log().setCapacity(6); // Maximum number of visible lines

// Add a timestamped event message
telemetry.log().add("Arm reached upper limit at %.1f s", runtime.seconds());
```

### VoltageSensor integration

The battery voltage is not a hardware device you configure in the Robot Configuration — it is discovered dynamically through the hardware map's `voltageSensor` iterable. The sample in `ConceptTelemetry.java` demonstrates the pattern:

```java
double getBatteryVoltage() {
    double result = Double.POSITIVE_INFINITY;
    for (VoltageSensor sensor : hardwareMap.voltageSensor) {
        double voltage = sensor.getVoltage();
        if (voltage > 0) {
            result = Math.min(result, voltage);
        }
    }
    return result;
}
```

Call this inside a telemetry lambda to display the minimum voltage across all hubs.

## Gamepad inputs

The `gamepad1` and `gamepad2` fields are available in every `LinearOpMode` and `OpMode`. They are updated by the SDK before each call to your loop code (before `loop()` in iterative OpModes, and continuously in `LinearOpMode`).

### Joystick axes

Both gamepads expose four analog axes, each returning a `float` in the range **-1.0 to 1.0**:

| Field | Description |
|---|---|
| `gamepad1.left_stick_x` | Left stick horizontal (positive = right) |
| `gamepad1.left_stick_y` | Left stick vertical (**positive = down** — negate for intuitive forward drive) |
| `gamepad1.right_stick_x` | Right stick horizontal (positive = right) |
| `gamepad1.right_stick_y` | Right stick vertical (positive = down) |

The "positive = down" convention for `left_stick_y` catches many beginners. Negate it when using the left stick for forward/back drive:

```java
double drive = -gamepad1.left_stick_y; // negate so pushing forward drives forward
double turn  =  gamepad1.right_stick_x;
```

### Trigger axes

```java
float leftTrigger  = gamepad1.left_trigger;  // 0.0 (released) to 1.0 (fully pressed)
float rightTrigger = gamepad1.right_trigger;
```

### Digital buttons

All buttons return `boolean`. The full set:

```java
gamepad1.a            // A / Cross
gamepad1.b            // B / Circle
gamepad1.x            // X / Square
gamepad1.y            // Y / Triangle
gamepad1.left_bumper  // LB / L1
gamepad1.right_bumper // RB / R1
gamepad1.dpad_up
gamepad1.dpad_down
gamepad1.dpad_left
gamepad1.dpad_right
gamepad1.start
gamepad1.back
gamepad1.left_stick_button   // clicking the left stick
gamepad1.right_stick_button  // clicking the right stick
```

### Controller compatibility

<Tabs>
  <Tab title="Xbox 360 / Xbox One">
    Fully supported. Both rumble motors (left/right) work. Button labels match the field names directly.
  </Tab>
  <Tab title="PS4 (DualShock 4)">
    Fully supported. Both rumble motors work. Cross = A, Circle = B, Square = X, Triangle = Y. The center touchpad is also readable (see below). The RGB LED is programmable.
  </Tab>
  <Tab title="Etpark (Xbox-style)">
    Broadly compatible. Rumble may only respond to `rumble1` and may only run at full power regardless of the value you pass. Test rumble behavior on your specific unit before the competition.
  </Tab>
  <Tab title="Logitech F310">
    Buttons and axes work normally. The F310 has **no rumble motors** — all rumble calls are silently ignored.
  </Tab>
</Tabs>

## Gamepad rumble (SDK 7.0+)

Rumble motors provide a haptic feedback channel that doesn't require the driver to look away from the field. Common use cases include: alerting the driver that endgame is approaching, confirming that an arm has reached a limit switch, or signaling when a sensor reading crosses a threshold.

<Warning>
  Do not spam rumble commands. Issuing rapid-fire rumble calls will truncate each previous rumble before it completes, resulting in a sputtering sensation rather than a clean signal. Issue rumble commands on **transitions** (the moment something changes), not on **states** (every loop iteration while the condition is true). Use `isRumbling()` to check before issuing a new command when overlap is a concern.
</Warning>

### Core rumble methods

**`rumble(double rumble1, double rumble2, int durationMs)`** — set both motor powers for a fixed duration:

```java
// Full-power both motors for 500 ms
gamepad1.rumble(1.0, 1.0, 500);

// Left motor only at 90% for 200 ms
gamepad1.rumble(0.9, 0, 200);

// Continuous rumble driven by trigger pressure (call each loop iteration)
gamepad1.rumble(gamepad1.left_trigger, gamepad1.right_trigger,
                Gamepad.RUMBLE_DURATION_CONTINUOUS);
```

Use `Gamepad.RUMBLE_DURATION_CONTINUOUS` as the `durationMs` argument when you want the rumble to persist until explicitly stopped (for example, while a button is held). Always call `stopRumble()` when the condition ends:

```java
if (gamepad1.left_bumper) {
    gamepad1.rumble(gamepad1.left_trigger, gamepad1.right_trigger,
                    Gamepad.RUMBLE_DURATION_CONTINUOUS);
} else if (leftBumperWasPressed) {
    gamepad1.stopRumble(); // Only stop once, on the release transition
}
```

**`rumbleBlips(int count)`** — fire a short sequence of evenly-spaced blips. Great for "3… 2… 1…" countdown signals:

```java
// Trigger three blips when button A is first pressed (transition, not state)
if (gamepad1.a && !lastA) {
    if (!gamepad1.isRumbling()) {
        gamepad1.rumbleBlips(3);
    }
}
lastA = gamepad1.a;
```

**`runRumbleEffect(Gamepad.RumbleEffect)`** — play a fully custom sequence built with the fluent builder API. Each step specifies power for each motor and a duration:

```java
Gamepad.RumbleEffect customEffect = new Gamepad.RumbleEffect.Builder()
    .addStep(0.0, 1.0, 500)  // Right motor 100% for 500 ms
    .addStep(0.0, 0.0, 300)  // Pause 300 ms
    .addStep(1.0, 0.0, 250)  // Left motor 100% for 250 ms
    .addStep(0.0, 0.0, 250)  // Pause 250 ms
    .addStep(1.0, 0.0, 250)  // Left motor 100% for 250 ms
    .build();

// Trigger it once when a time threshold is crossed
if (runtime.seconds() > HALF_TIME && !halfTimeRumbled) {
    gamepad1.runRumbleEffect(customEffect);
    halfTimeRumbled = true;
}
```

**`isRumbling()`** — returns `true` if any rumble action is still in progress. Use this to avoid cutting a blip sequence short:

```java
if (!gamepad1.isRumbling()) {
    gamepad1.rumbleBlips(2);
}
```

**`stopRumble()`** — immediately cancels any ongoing rumble or custom effect.

<Tip>
  Issue rumble commands on **state transitions**, not on the state itself. For example, trigger a blip the moment a touch sensor is pressed (`currentTouch && !lastTouch`), not every loop iteration while it is held down. This single habit eliminates 90% of accidental rumble spamming.
</Tip>

## PS4 touchpad

The Sony DualShock 4 gamepad includes a central capacitive touchpad that can detect up to two simultaneous finger touches. The `Gamepad` class exposes these as six new fields (added in SDK 7.0):

```java
// First finger
if (gamepad1.touchpad_finger_1) {
    float x = gamepad1.touchpad_finger_1_x; // -1.0 (left) to +1.0 (right)
    float y = gamepad1.touchpad_finger_1_y; // -1.0 (bottom) to +1.0 (top)
    telemetry.addLine(String.format("Finger 1: x=%5.2f y=%5.2f", x, y));
}

// Second finger (multi-touch)
if (gamepad1.touchpad_finger_2) {
    float x = gamepad1.touchpad_finger_2_x;
    float y = gamepad1.touchpad_finger_2_y;
    telemetry.addLine(String.format("Finger 2: x=%5.2f y=%5.2f", x, y));
}
```

**Coordinate system:** origin `(0, 0)` is the center of the touchpad. The top-right corner is `(1.0, 1.0)` and the bottom-left corner is `(-1.0, -1.0)`.

Practical applications include: swipe gestures to trigger autonomous sequences, two-finger pinch to adjust a speed multiplier, or simply pressing the touchpad as an extra button (it registers as `gamepad1.touchpad`).

## PS4 LED

The DualShock 4's RGB LED bar can be set from your OpMode. This is useful for visual alliance colour confirmation or status indicators visible to the drive team:

```java
// Set the LED to a specific RGB colour (values 0–255)
gamepad1.setLedColor(255, 0, 0, Gamepad.LED_DURATION_CONTINUOUS); // Red
gamepad1.setLedColor(0,   0, 255, 1000);                           // Blue for 1000 ms
```

The LED reverts to the default Driver Station colour assignment when the OpMode ends.

## Putting it all together

The following snippet combines several patterns from `ConceptTelemetry.java`, `ConceptGamepadRumble.java`, and `ConceptGamepadTouchpad.java` to show how feedback flows in a typical TeleOp loop:

```java
// Track previous button state for transition detection
boolean lastA = false;

while (opModeIsActive()) {
    boolean currentA = gamepad1.a;

    // --- Drive ---
    double drive = -gamepad1.left_stick_y;
    double turn  =  gamepad1.right_stick_x;
    robot.driveRobot(drive, turn);

    // --- Rumble on button press transition (not state) ---
    if (currentA && !lastA) {
        if (!gamepad1.isRumbling()) {
            gamepad1.rumbleBlips(2);
        }
    }
    lastA = currentA;

    // --- Telemetry ---
    telemetry.addData("Drive", "%.2f", drive);
    telemetry.addData("Turn",  "%.2f", turn);
    telemetry.addData("Battery", "%.1f V", getBatteryVoltage());
    telemetry.addData("Rumbling?", gamepad1.isRumbling() ? "YES" : "no");
    telemetry.update();

    sleep(10);
}
```
